# CLAUDE.md (task)

Own skill, living in `~/Projects/skills/skills/task` (the shared repo, see its root CLAUDE.md); `~/.claude/skills/task` links here. Edit and commit here.

- Works with its sibling `flow` (`skills/flow`): `plan` and `review` follow `flow`'s SKILL.md, and `status.py` reads `flow`'s `feature.yaml` (`status`, `repo`, `story`). Change both together when the feature format moves.
- `extensions/<name>/` holds the rules of one kind of source (today `aha`), loaded only when `SKILL.md`'s Extensions section recognises it. Keep `SKILL.md` free of that source's rules: add a step override to the extension's file, not here.
- `config.yaml` holds the home (`~/Projects/home`); it is gitignored, and `config.example.yaml` is the versioned copy (SETUP.md copies it). The folder format is `reference/format.md`.
- `scripts/commands.py` writes the YAMLs of each `task.py` command (journal, decisions, validations, pending, brief date) by line edits with the repo's `lib/` (`yamledit`, `yamlio`), the same helpers `flow` uses; `status.py` only reads, through `model.py`, which uses `lib/yamlio`. A helper that knows nothing of this skill's files goes in `lib/`, not here. Add a command for any field an id, date or status gets typed into: its edit in `commands.py`, its arguments and its entry in `EDITS` in `task.py`.
- `task.py` parses the arguments and runs a command in one order: the command's edit (`commands.py`), one load (`status.Task`), the sync from that load (`sync.py`), then one check over a `Task` built on the same model. `sync.py` reads through the model, writes a file only when it changes and puts what it wrote back with `Model.put`, so the check reads no file twice. `task.py` loads `commands.py` and `sync.py` by file path (`task_commands`, `task_sync`) and `status` by name: it runs only as a script, whose folder Python puts on `sys.path`, and the tests patch that `status` module.
- Status is written, never typed: `task.py sync` fills `acs.yaml` (requirements, items) and, through `flow`'s `roadmap.py` (`sync_roadmap`), `roadmap.yaml`; `status.py` fails on a missing or stale one, with the same rule (`roadmap.py`'s `statuses`).
- `status.py` loads `flow`'s `scripts/roadmap.py` by its file path as `flow_roadmap` (`lib/modules.py`); `checks.py` and `sync.py` load it the same way and get that same module, cached by its name, never by putting `flow/scripts` on `sys.path`, so a module here named like one of flow's stays our own. The machine of each entity is the table in `reference/format.md`: change it and the scripts and tests together.
- `status.py` parses the arguments and holds the `Task` facade (loading, delegates, `check`, `collect`, `find`); the rest lives in modules of its own, each loaded the same way by file path as `task_<module>`, never by putting `scripts/` on `sys.path` (the dashboard loads `status.py` in a process whose path holds its own modules). The names task.py, the tests and the dashboard import stay on `status.py` as aliases.
  - `model.py` is the one place a task file is read: each file once per load, as raw text, LF text, parsed YAML or frontmatter; `story()` is the one reader of a feature's story.
  - `derive.py` holds what the files imply (decision trees, the features of each decision, `req_status`, `item_status`, `missing`, the agenda), each computed once per load, and fails nothing.
  - `checks.py` holds every consistency check and reports the failures; `born_from` cycles go through `lib/graph.find_cycle` only.
  - `step.py` holds the next step and who it waits on; its `unproven()` is the one rule for an item neither concluded nor with a `pr_note`, read by the review step and the pr gate.
  - `gates.py` holds the gates, the PR notes and the links between features and decisions.
  - `brief.py` holds the sources digest and the brief's generated blocks; `report.py` renders the text report from `collect()` and the decision statuses.
  - A new reader goes through the model, a new derived value through `derive.py`, a new check into `checks.py`.
- `scripts/status.py` needs PyYAML. Its tests drive the CLI, except a module test whose criterion is the module's boundary (what it reads, how often), which calls the module directly (`test_model`, `test_derive`, `test_report`); `test_sync` drives the CLI but counts the files it opens, since one read per file is its criterion; the repo root pre-commit hook runs them when this skill is staged (command: its `test:` in the root `skills.yaml`).
- Commits: Conventional Commits in English, subject states the why, stage files by name.
